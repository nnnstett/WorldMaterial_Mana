# 執筆ルール

World Material "Mana" のドキュメントを書くときに守るルール。
本書は規約のうち**書式・テンプレート・閾値の正**である。各規則の意味・判断規準・
論拠の正は [`architecture.md`](architecture.md) にあり（所有分担は
[同 §1.4](architecture.md#14-規約の所有分担)）、本書はそれを再掲せず参照する。

## 1. ファイルの種別と役割

| 種別 | 場所 | 役割 |
|---|---|---|
| 核 | `world/core/axioms.md`, `theorems.md`, `open-questions.md` | 公理 E/I・定理 T・未解明領域 Q を定義する |
| 応用 | `world/*.md`（核以外） | 核を参照しつつ個別ドメインを記述する |
| 用語集 | `glossary.md` | 全 ID の一覧 |
| メタ | `docs/*.md` | 設計方針・計画・本ルール集。構造規約の適用外 |

本ルール集の §2〜§11 は **核・応用・用語集** に適用される。§12（画像アセット）
はリポジトリ全体の画像に適用される。
メタ文書（`docs/`）は禁止語や NG 例を本文に含める必要があるため、構造・禁止語
・分量のルールは適用しない。

## 2. 応用ファイル冒頭の前提行

応用ファイル（`world/` 直下の核以外）は **冒頭 8 行以内** に依存する公理・
定理を明示する。

```markdown
*前提: [T7 魔法](core/theorems.md#t7-魔法), [E6 精神エネルギー](core/axioms.md#e6-精神エネルギー)*
*関連: [T5 存在強度#ビッグバン由来物質の還元不可能性](core/theorems.md#重要な帰結-ビッグバン由来物質の還元不可能性),
       [Q1 真度操作](core/open-questions.md#q1-真度を人為的に深くする方法)*
```

「前提」という語をヘッダ近傍に必ず含める。

## 3. 相互参照のリンク形式

### 3.1 リンクの書き方

| 場面 | 形式 |
|---|---|
| 同一ファイル内 | `[E1 現界](#e1-現界)` |
| `core/` 内の異ファイル | `[E1 現界](axioms.md#e1-現界)` |
| 応用 → `core/` | `[E1 現界](core/axioms.md#e1-現界)` |
| `core/` → 応用 | `[magic.md](../magic.md)` |
| 応用同士 | `[races.md](races.md)` |
| 応用ファイル内の節 | `[現化魔法](magic.md#現化魔法)` |
| 定理内「重要な帰結」節 | `[T5#ビッグバン由来物質の還元不可能性](core/theorems.md#重要な帰結-ビッグバン由来物質の還元不可能性)` |
| 公理項目（適用範囲は §3.3） | `[E5 魂#大きさ](axioms.md#e5-大きさ)` |

アンカー名は GitHub の Markdown レンダリング規則（小文字化・空白のハイフン化・
日本語見出しはそのまま）。リンクテキスト先頭の ID と参照先見出しの ID は一致
させる。参照先のファイル・アンカーは必ず実在させる。

書式の使い分け: インライン引用（`[X 名称] と [Y 名称] により…` の形）は、リンク先が
主張の成立を支えている場合に用いる。用語の指し先・補助的な参照は動線形式
（`（→ [X 名称]）`）で書く（判断規準は
[`architecture.md` §4.4](architecture.md#44-相互参照のリンク形式)）。

### 3.2 散文での参照禁止

命題（E/I/T/Q）を本文中で指すときに、コードのみ・括弧のみで書かない。
必ずセクション名を含むリンクで書く。範囲・列挙も例外ではない。

```
NG: T1 により、エネルギーは保存される
NG: マナの状態（[T1]）が安定する
NG: T1〜T6 はエネルギー保存系
NG: 対象は T1, T5, T7 である
OK: [T1 エネルギー保存則](theorems.md#t1-エネルギー保存則) により、エネルギーは保存される
OK: 本文で [T1 エネルギー保存則] と書き、ファイル末尾に
    [T1 エネルギー保存則]: theorems.md#t1-エネルギー保存則 を定義する shortcut reference 形式
OK: [I1 変換則#量の保存](axioms.md#i1-量の保存) により、逆向きの変換も量を保つ
    （項目アンカー参照。適用範囲は §3.3）
OK: [T1 エネルギー保存則] 〜 [T6 同調] のように、範囲は両端を、
    列挙は各要素をリンクで書く
```

引用（`>` 行）・コードブロック・インラインコード内は対象外。
禁止されるのは番号・コードのみの表記であり、セクション名を含む項目アンカー参照
（§3.3）はこの禁止に当たらない。

### 3.3 公理項目アンカー

公理の**項目**を項目粒度で引用するための名前付きアンカー。公理項目は
独立 ID を持たない（§5）ため、安定した名前のアンカーで参照する。

- **配置**: 参照される公理項目の**行末**に `<a id="e5-大きさ"></a>` を置く
  （生 Markdown の読みやすさを優先した行末配置）
- **命名**: `小文字の群ID-スラッグ`。接頭辞は所属する公理群の ID と一致させる。
  スラッグに空白は使わない（日本語可）
- **スラッグ**: 項目の**肯定的主張**の安定した名前を付け、項目の主張が変わらない
  限り変えない（NG: 「方向づけがない」ことを述べる項目に `i1-方向づけ`／
  OK: `i1-無方向現出`）
- **リンクテキスト**: `[E5 魂#大きさ]` のように「群の ID・名称＋`#`＋スラッグ」で書く
- **参照定義**: shortcut reference 形式（本文で `[E5 魂#大きさ]` を使い、参照元
  ファイルの末尾に `[E5 魂#大きさ]: axioms.md#e5-大きさ` を定義する。§3.2）を
  推奨する。参照定義の行は本文の参照ではないため、適用範囲の判定は本文中の
  使用位置で行う
- **適用範囲**: 項目アンカーへの参照は `world/` 配下でのみ使う（機械検査）。記述が特定の
  項目の内容に依存するとき（定理の証明スケッチのステップ引用、項目間の関係を主題として
  述べる記述など）に用いる（判断規準の正は
  [`architecture.md` §4.4](architecture.md#44-相互参照のリンク形式)）。インライン引用・
  動線（`（→ …）`）のどちらの書式でも使ってよい。用語の指し先・純粋なポインタは
  群単位リンクで書く

命名・一意性・所属一致・行末配置、および `world/` 配下限定は機械検査される（規約条項と
チェック ID の対応は [`architecture.md` §5.5](architecture.md#55-保証マップ)）。スラッグが
肯定的主張の安定名になっているか、参照が項目への依存を伴うか（純粋なポインタでないか）
は、レビューで確認する。

## 4. 命題セクションの構造

### 4.1 公理（E/I）・定理（T）

**公理（E/I）は概念単位の公理群**として、次の順序で書く。

1. **リード文**（必須）— 見出し直下に**無ラベル**で 1〜2 文。群の要約であり、
   それ自体は規範を持たない（規範は「公理」リストが担う）。公理 1 の言い換えに
   留めず、複数の項目を束ねる**見取り図**として書く
2. **公理**（必須）— 番号付きリスト。各項目は原則 1〜2 文の独立した根本前提。
   番号は読みやすさのための連番で、本文からの参照に使わない（参照は ID 単位）。
   `**公理**` の見出しから README の凡例節へリンクする
3. **役割セクション**（任意）— **定義** → **観測事実** → **目安** → **補足** →
   **空白** の固定順で、該当する役割だけを `**役割名**:` として置く。
   セクション内の箇条の先頭には必要に応じて `**見出し語**:`（定義では用語名）を置く
4. **関連**（必須）

公理リストの書き方:

- 項目は**仮定そのもの**だけを述べる。仮定から導ける帰結は **補足** へ、
  例外・傾向の観測は **観測事実** へ、未解明への言及は **空白** へ移す。
  誤読を防ぐ適用範囲の限定（スコープ注記）は項目内の括弧で残してよい
- 同じ主題の複数の仮定は 1 項目に束ねてよい。「片方だけを変える派生作品の
  改変が自然に想像できる」仮定は別項目に分ける
- 順・逆など対称に成り立つ仮定は、項目を複製せず 1 項目に束ねて対称性を一文で
  言う。原則 1〜2 文に収まらない場合、または片側にだけ固有の条件・帰結があり
  片側だけを変える改変が自然に想像できる場合は分割してよい
- 項目内の動線（→ …）は、その項目が使う語・条件の指し先（初出の割り注・例外の
  行き先・スコープ注記）に限る。主張の成立に関わらない誘導は補足に置く
- 「通常」「原則として」等のヘッジ語は、例外の行き先（観測事実・空白・定理）が
  辿れる場合にのみ使う。行き先がなければ言い切る
- 役割セクションの **定義** で定める属性語を項目内で使う場合、初出時に括弧で
  最小の意味を添える（例: 「真度（マナとの共鳴のしやすさ）」）
- **空白** の箇条は対応する未解明領域（Q）へのリンクを必ず伴う

**定理（T）は単一の導出命題**として、次の順序で書く。`**命題**` `**導出元**`
`**証明スケッチ**` `**関連**` は必須。

1. **命題**（必須）— 1〜2 文。公理が単独では述べていない導出増分だけを主張し、現象そのものは公理を引用する
2. **導出元**（必須）— どの公理群・定理から導かれるか
3. **証明スケッチ**（必須）— 各ステップは導出元だけを、群単位リンクまたは項目アンカー参照（§3.3）で引用する（条項番号（番号のみの表記）は本文に書かない。用語の定義参照は前提使用に数えない）
4. **詳細**（任意）— 命題・導出元から導かれる内容のみ。「公理」リストは置かない
5. **役割セクション**（任意）— 定義 → 観測事実 → 目安 → 補足 → 空白 の固定順で、該当する役割だけを置く
6. **重要な帰結**（任意。節として書き、独立 ID は付けない。節の中でも役割セクションを使える。固定順はスコープ（エントリ直下・各節内）ごとに適用する）
7. **関連**（必須）— 他命題・応用ファイルへのリンク

```markdown
### [T1] エネルギー保存則

**命題**: 系全体のエネルギー総量は保存される。

**導出元**: [E1 現界](#e1-現界), [E2 真界](#e2-真界), [I1 変換則](#i1-変換則)

**証明スケッチ**:
- [I1 変換則](#i1-変換則) により、変換は量を保つ
- ...

**詳細**:
- 物理エネルギー・マナ・精神エネルギーは [I1 変換則](#i1-変換則) により互いに変換可能
- ...

**関連**:
- → [T2 ビッグバン](#t2-ビッグバン), [magic.md](../magic.md)
```

**行使形態の定義**（`## 行使形態の定義` 節下の T）は、導出される法則ではなく
行使方法への命名であり、次の順序で書く。`**定義**` `**定義対象**` `**関連**` は
必須。命題・導出元・証明スケッチ・「公理」リストは置かない。

1. **定義**（必須）— 「〜する場合、これを「X」と呼ぶ」の形。1〜2 文
2. **定義対象**（必須）— どの法則の行使への命名か（「〜の行使のうち…」のように書き、導出を装わない）
3. **詳細**（任意）— 定義対象の機構から導かれる内容のみ
4. **役割セクション**（任意）— 観測事実 → 目安 → 補足 → 空白。役割としての **定義** は置かない（用語の定義は公理・応用ファイルに委ねる）
5. **関連**（必須）

役割セクションの語彙は **定義** / **観測事実** / **目安** / **補足** / **空白** の
5 種のみ（概念的な土台は [`architecture.md` §4.10](architecture.md#410-詳細内の役割ラベル)）。
未解明領域（Q）は対象外。応用ファイルは任意（用いる場合は同じ語彙に従う）。
1 箇条 1 役割とし、複数の役割が混在する箇条は分割する。入れ子の箇条は属する
セクションの役割を引き継ぐ。

### 4.2 未解明領域（Q）

次の 4 ラベルを必ず含める。

```markdown
### [Q1] 真度を人為的に深くする方法

**背景**: 既知の事実と未解明部分の境界。
**現在判明していること**: 観測事実、関連組織の認知レベル。
**この空白の意図**: 物語ギミック・派生作品での活用例。
**関連**: [T3 マナ濃度](theorems.md#t3-マナ濃度), [dungeon.md](../dungeon.md)
```

## 5. ID と分類

- **接頭辞**: `E`（存在公理）/ `I`（相互作用公理）/ `T`（定理）/ `Q`（未解明領域）
- E/I の ID は概念単位の**公理群**を指す。群内の公理の番号は ID ではなく、
  本文からの参照に使わない（NG: 「E5 の公理 3 により…」）
- **採番**: 各分類で末尾連番（`E7`, `I5`, `T10`, `Q7` ...）
- **見出し書式**: `### [E1] 名称`
- 同一ファイル内で **同じ ID を 2 回使わない**
- 廃止された ID は **再利用しない**。`[廃止] T3 旧名称 — 移動先` の痕跡を残す
- 命題が肥大化したら分割記号（`E3a`, `E3b`）を使わず **新 ID を採番** し旧 ID を
  廃止扱いにする
- 定理内「重要な帰結」節および応用ファイル内の節は **独立 ID を持たない**
- 公理群内の個々の公理項目も **独立 ID を持たない**（項目粒度の参照は
  名前付きアンカーで行う。§3.3）

## 6. 用語集

`world/core/` で定義した全 ID は `glossary.md` に登場させる。新しく命題を
追加したら `glossary.md` にも 1 行追加する。

エントリは単体で読める自己完結の一文とし、そのための本文の再述を許容する。
ただし**出典リンクは、その事実の規範を持つ命題（正。
[`architecture.md` §4.11](architecture.md#411-記述の正の一意性)）と一致させる**。
別の命題が同じ事実に触れていても出典には正だけを書き、正が移動したら出典も
追随させる。

見出し語は、出典先の本文に同一の語（または出典側で明示された別名）として
現れるようにする。出典を辿った読者がその語に出会えない状態
（用語集だけの造語）を作らない。

## 7. 禁止語と廃止コード

本文（引用・コードブロックを除く）に次を書かない。

- **「補題」** — 数学用語。中学生〜の読者を想定した本作では使わない
- **「波長」** — 旧用語。真度（マナとの共鳴のしやすさ）と位相（個体間の適合。かみくだき「チャンネル」）に分離して廃止。旧称として言及する場合はインラインコードで書く
- **`L#` 接頭辞** — 旧「補題」コード（廃止）
- **`C#` 接頭辞** — 旧「系」コード（廃止）

「体系」「系統」のような通常の複合語、ダンジョン分類の `C-1` `C-2` のような
ハイフン区切り表記は対象外（区別される）。

## 8. パス

次の旧パスにリンクしない。再構築前のファイル名・ディレクトリ構造の名残。

```
世界の法則.md   魔法.md   魔術.md   超能力.md   種族.md
/dungeon.md     character/   history/
```

新パスは `world/` 配下・英字名（例: `magic.md`, `spellcraft.md`, `dungeons.md`,
`psionics.md`, `races.md`, `artifacts.md`）。最終形は
[`architecture.md` §3 ディレクトリ構成](architecture.md#3-ディレクトリ構成) を参照。

## 9. 分量上限

執筆の暴走防止のための上限。

| 対象 | 上限 |
|---|---:|
| 命題・定義主部（`**命題**`／行使形態の定義の `**定義**` 直後）の文数 | **2 文** |
| 見出しレベル | **H4** まで |
| 連続するリスト項目 | **12 項目** |
| 応用ファイル全体の行数 | **400 行** |
| 1 命題エントリの本文字数（リンク部分を除く）— 定理・応用 | **1500 字** |
| 1 公理群エントリの本文字数（同上）— 警告 1500 字＝グルーピング見直しのシグナル | **2000 字** |

意図的に超過させる場合は §11 の例外コメントを使う。
公理群の字数は命題分割ではなく**グルーピング見直し**（概念の切り出し）を
検討するシグナルである（`architecture.md` §4.1）。

## 10. ToDo を本文に置かない

書きかけ・課題は **GitHub Issue** で管理する。本文（`world/` 配下・
`glossary.md`）に `TODO:` / `FIXME:` / `- [ ]` や `## ToDo` 節を置かない。

## 11. 例外コメント

分量上限（§9）を意図的に超えたい場合、対象の **直前** に次のコメントを置く。

```markdown
<!-- check:length-exempt 列挙網羅が目的のため -->
- 項目 1
- 項目 2
- ... 16 項目続く
```

- 直後の **非空ブロック**（空行で挟まれた最初の塊）の分量上限が解除される
- 解除されるのは分量のみ。リンク切れ・必須セクション欠落・禁止語・旧パスは
  例外コメントでは免除されない
- 禁止語・旧パスを文書例として本文に含めたい場合は、引用（`>`）または
  コードブロックの中に入れる

## 12. 画像アセット

種別ごとの置き場所と形式（意味・判断規準は
[`architecture.md` §4.8](architecture.md#48-図画像の管理)）。

| 種別 | 場所 | 形式 |
|---|---|---|
| 構造図 | `world/images/` | ソース（drawio 等）と書き出し（`.svg`）の両方を置く |
| イメージボード | `images/` | `imageboard-<主題>.jpg`（JPEG） |

イメージボードは生成時の解像度のまま保存し、掲載のための縮小をしない。掲載箇所
にはキャプションとして「イメージボード」と記す。
